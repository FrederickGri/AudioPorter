## 仓库核心组件

| 内容 | 位置 |
| --- | --- |
| 下载引擎、界面、工作进程与平台适配 | `audioraven/`、`main.py` |
| 锁定的运行和构建依赖 | `requirements.txt`、`requirements-dev.txt` |
| 原生构建入口 | `build_app.py`、`assets/`、`scripts/` |
| 用户指南和兼容性范围 | 两种语言的 README、`docs/` |
| 原创代码许可证与依赖声明 | `LICENSE`、中文译文、两种语言的第三方声明、`licenses/` |
| 回归测试和原生构建验证 | `tests/`、`.github/workflows/` |
| 贡献、安全和问题模板 | 中英文 CONTRIBUTING / SECURITY、`.github/ISSUE_TEMPLATE/` |
| 版本记录 | 中英文 CHANGELOG |
| 隐私排除规则 | `.gitignore` |

GitHub 创建仓库并不强制要求上面所有文件；这些组件用于让应用可使用、可维护。不要把旧 `dist/`、备份、本地 spec、Cookie 或日志提交到 Git。原生 ZIP 和校验值属于发行附件。

## 发布步骤

1. 更新 `audioraven.__version__`、两种 README 的文件名以及中英文更新记录。
2. 各平台执行测试、打包和打包应用检查。验证完整解压目录；仅源码测试通过还不够。
3. 对暂存源码和解压发行包执行隐私扫描，检查提交的作者与提交者信息，不使用个人邮箱或主机用户名。
4. 收集实际构建的依赖声明。按 LGPL / GPL 要求保留相应源代码的访问渠道，包括 FFmpeg 启用的库及构建脚本，必要时与发行包一同提供。
5. 推送匹配版本的附注标签，如 `v0.3.0`。CI 会拒绝版本不符的标签，完成三个平台构建后才创建**草稿发行版**。每个 ZIP 均附 SHA-256 校验值。
6. 核查草稿中的测试结果、依赖源码可用性和桌面验收状态，满足要求后发布。未做的 Windows 11 交互检查应明确记录，不能写成已通过。

手动触发工作流只构建软件包，不创建公开发行版。拉取请求执行相同的原生测试与构建检查，但仅拥有仓库只读权限。CI 不需要个人账号 Cookie；只有标签发行任务有写权限。官方 Actions 固定到提交哈希，Dependabot 提出更新建议。
